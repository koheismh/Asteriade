# GitHubを使った設計・研究成果の記録方針（ドラフト）

- 記録日: 2026-10-21
- 状態: レビュー用 / 未マージ
- 対象: Asteriadeの設計議論、AIによる研究サイクル、将来の開発・検証結果

## 基本方針

GitHubには、**次のAIがこのチャットを知らなくてもプロジェクトの現在地を理解し、再開できる情報**を保存する。

- 人間向けの短い現在地サマリーと、AI向けの明示的な引き継ぎ事項を両方残す。
- 決定事項と提案・未決事項を混同しない。
- 実験失敗・不採用の反論・検証不能・未探索範囲を消さずに残す。
- 研究コード、実験プロトコル、使用データ、成果物の同一性を識別できるようにする。
- 会話の全文保存ではなく、意思決定・証拠・再開点を要約して永続化する。
- 外部ストレージの成果物は参照・ハッシュ・有効期限を記録する。短期CIアーティファクトだけに依存しない。

## 推奨する更新契機

- 設計の重要な方針が決まったとき
- 実装段階/研究Milestoneが完了したとき
- 仮説を採否したとき、または新しい研究方向に転換したとき
- 最終検証・科学実装・データ品質で重要な問題が見つかったとき
- 作業を中断し、別のAI/セッションへ引き継ぐとき

更新のたびに、**変更した文書 / 変更理由 / 未解決事項 / 次の行動**を明確にする。

## 推奨ファイル構成（段階導入）

```text
docs/
  research/
    RESEARCH_DESIGN_PROPOSAL_2026-10-21.md   # 現時点の設計提案
    GITHUB_RECORDING_POLICY.md               # 本文書
    HANDOFF.md                                # 次のAIが最初に読む現在地
    DECISIONS.md                              # 日付・判断・根拠・代替案
    protocols/                               # 凍結済み実験計画
    reports/                                 # 市場別/仮説別/サイクル別報告
    manifests/                               # JSONによる実験・成果物ID
```

このレイアウトは提案であり、すべてのディレクトリを先行作成する必要はない。

### HANDOFF.mdに必ず記載する内容

1. 現在の製品方向性と正式な要件の所在。
2. 今どのフェーズなのか。完了・進行中・中断・未開始を明示。
3. 最新の**承認済み**設計判断と、その判断の理由。
4. 変更してはいけない研究・権限・安全上の境界。
5. 調査済みの事実と、未検証の仮説の区別。
6. 次の具体的な作業、完了判定、必要な承認。
7. 参照すべきレポート・コード・データの参照先。
8. 再現性の制限や失効した成果物の有無。

### 個別の研究レポートに必ず記載する内容

`hypothesis_id / cycle_id / experiment_id / market / instrument / period / data_id / code_sha / parameters / seed / cost_scenarios / execution_model / tested_variants / untested_variants / statistical_checks / results / review_issues / manager_decision / next_steps / artifact_refs / reproducibility_status`。

技術的な条件は機械可読JSONにも保存し、人間向けMarkdownはそのJSONと照合できるようにする。

## GitHub更新の安全なワークフロー

1. 現在のブランチと既存の要件を確認。
2. 文書を専用ブランチで追加・改訂する。
3. 公開範囲、機密情報、個人情報、Git差分を確認。
4. PRを作成し、人間が確認してから正式要件へマージする。
5. マージ後は引き継ぎ文書を更新し、最新の正本への参照を保持する。

初期Asteriadeリポジトリは**public**である。口座、認証情報、個人的な投資額や許容損失、APIキー、秘密の研究データを公開コミットしない。必要な場合はローカルや専用の非公開保存先へ分離する。

チャットで話しただけでGitHubへ自動的に継続保存されるとは想定しない。チャット側が保存作業を実行する場合は、接続が使えること、更新対象、公開範囲、必要な承認を毎回確認し、実際のGitHub反映結果を明示する。

## レポート品質チェック

- AIの「完了した」という自己申告だけで確定しない。
- 実験の合格基準や使用コストを結果確認後に隠れて変更しない。
- 使用したデータと最終確認用データの独立性を正しく記録する。
- 再現に必要な成果物が無いなら、再現可能とは主張しない。
- 次のAIが未承認の提案を確定要件と取り違えない。
