# Asteriade 実装スコープ再評価・段階縮小提案（2026-10-21）

> **状態：レビュー用の変更提案（未承認・未統合）。** 既存 `docs/REQUIREMENTS.md` と `docs/IMPLEMENTATION_PLAN.md` は本書だけでは置換しない。Codexの稼働中ブランチを直接変更しない。

## 0. 結論

現行要件の研究上の厳密さは保ち、**初期MVPの機能量と各種技術の同時開発を縮小する**。現時点で実装済みのGo/SQLite/loopback基盤と `internal/research` の合成Spec/freeze identityを廃棄する必要はない。旧BTC研究や既存エンジンを確認する前に、新しい汎用会計・執行・統計エンジンを作らない。

目標の階層を次のように分ける。

1. **長期目標**：複数AIが議論し、反証可能な投資仮説を自律探索・検証し、知識を蓄積する。
2. **最初の利用可能な研究MVP**：単一市場、単一Manager、既知の計算検査、固定/再利用エンジン、最小進捗表示、知識レポートで、仮説→バックテスト→比較→記録を人間の逐次指示なしに完走する。
3. **価値が確認できた拡張**：独立Reviewerによる有限討論、より広い自律探索、GA、Prospectiveの自動追跡、追加市場。

「仮説の発見能力」「正しい検証能力」「複数AIの追加効果」「ユーザーの時間節約」を**別の達成指標**とし、利益が出る戦略の発見をソフトウェアMVPの必須合格条件にしない。

## 1. 外部レビューの採否

| 論点 | 判断 | 理由・条件 |
|---|---|---|
| 個人開発に対しMVP過大 | **採用** | 最小縦断フローを先に作り、高度機能は段階導入 |
| Stage 1で5段階複数AI討論を必須にする | **変更提案** | 先に単一Manager＋機械ゲート（B）を完走、後から同じ環境へReviewerを追加。討論自体は廃止しない |
| 要件と実装技術を分離 | **一部採用** | Windows 11/配布容易/外部DB不要/追加費用制限はユーザー要件。Go/SQLite/Provider SDKは設計選択・変更可能として管理 |
| 仮説の創出が弱い | **採用・最重要** | 市場メカニズムから仮説を生成する入力経路と反証の設計を追加 |
| 月3,000円に全データを収められる保証がない | **採用** | 予算を必須制約として扱い、高品質データの調達を保証しない。価格/権利/必要精度が折り合わなければscope縮小/停止 |
| Market Knowledgeが未定義 | **採用** | 主要成果物に市場知識カタログを追加 |
| 文書の重複 | **採用** | 一枚の簡潔なProduct Requirements＋別紙の研究プロトコル/セキュリティ/アーキテクチャに分割 |
| OSSエンジン優先 | **条件付き採用** | Stage 0Bで旧quant-btc-labと絞ったOSS候補を、正解fixture・権利・Windows制約で比較する。無検証採用しない |
| 初期市場を必ず1年間固定 | **不採用** | 期間は恣意的。暗号資産現物1市場を初期対象とし、他市場は研究フローの有効性と必要データを検証後に解禁 |
| Prospectiveを完全にStage 3以降へ | **一部採用** | 自動追跡は後回しにできるが、凍結時点と将来のシグナル記録契約は初期から保護する |
| 撤退条件がない | **採用** | 研究の「利益がない」だけでなく、ソフト開発の費用対効果に対するレビュー/縮小基準を設ける |
| 初期UIをCLIのみにする | **一部採用** | 豪華な外観は後回し。ただしユーザーが最も困った「今何を研究中か・いつバックテストか・終わったか」を示す最小Web画面はMVP必須 |

## 2. 次に開発する順序（提案）

| 段階 | 対象 | 出口条件 |
|---|---|---|
| 現在：Stage 0A | 実装済みのfreeze identity（Go） | 既存テストは保持。現時点で研究エンジンの正しさを主張しない |
| **次：Stage 0B** | 旧quant-btc-labおよび既存エンジン再利用のread-only比較 | 採用候補、捨てる部分、独立計算テスト、データ要件の一覧を提出 |
| Stage 0C/0D | 合成価格で最小kernelのgolden vectors、必要なWindows安全境界とholdout metadata試験 | 再現可能な合成約定・会計、境界が未合格のRunnerは起動拒否 |
| **Stage 1A** | 1市場・単一Manager（B方式）・少数の仮説・共通kernel・事前baseline・最小Cockpit・Markdown/JSON報告 | 少なくとも1つの否定的/肯定的仮説が自動で正しく完走。利益発見は不要。停止/失敗状態を見せる |
| Stage 1B（価値検証） | Reviewer反論→Manager回答→必要なら再反論→Manager最終決定を追加 | 同じゲートを通したBとの比較記録、討論は最大2ラウンドで必ず終了。費用/時間/欠陥発見を計測 |
| Stage 2 | 研究プログラム横断の検索・探索/選抜補正高度化、必要時GA、prospective自動化 | 研究数ではなく、有効な独立検証、知識蓄積と効率を測定 |
| Stage 3 | FX/日経225mini等の市場拡張、UI/クラウドの必要部分 | 市場個別の仕様、データ権利、会計・安全fixtureが通った範囲のみ |

Stage 1Aと1Bは、同時に全面実装しない。同一製品の連続した小規模リリースとしてよい。後から独立Reviewerを追加できるよう、最初から研究計画・レビューコメント・判断の記録スキーマを柔軟にする。

## 3. 仮説生成を研究機能として定義する

「テクニカル指標をランダムに組み合わせる」以外の情報源・発想経路を明確にする。最初から全ソースを使う必要はない。

**候補生成の入力経路**：
- 市場構造と価格形成：流動性、取引時間、参加者の制約、注文執行・需給。
- 時間・レジーム条件：日次/週次時間帯、変動率、出来高、急変後の挙動。
- 外部の公開研究・既知の異常現象：出典と検証可能な形への変換（情報利用可能時刻を含む）。
- 失敗研究からの説明：どの予測が否定され、何が未検証かから反証可能な別仮説を起こす。
- 探索カバレッジの穴：Entry/Exit/Position/Riskのどこを試していないか。ただし探索数だけを増やさない。

**仮説カードの必須項目**：
`mechanism / observable / market_condition / predicted_effect / alternative_explanation / falsification_test / minimum_data / information_availability / cost_risk / baseline / priority_rationale`

Managerは「なぜ今これを優先したか」を短文で残す。主観点を成功確率と誤表示しない。データが揃わなければ、不明や保留と表示する。新規性は派手な指標ではなく、反証可能な市場メカニズムの有無で評価する。

## 4. Market Knowledge：研究成果の主表示

仮説・市場現象を検索できるカタログに蓄積する。収益戦略の発見がなくても、どの説明がどの条件で棄却されたか利用可能にする。

最低限：
- 現象名、観測対象市場・期間、研究ID、原因説明/対立説明。
- 状態：`idea / investigating / rejected_in_tested_scope / promising_exploratory / holdout_checked / prospective_pending / prospectively_observed / invalid`。これは科学的確証を意味しない。
- 検証した条件と未検証条件、採用した比較対象、結果と推定の不確実性。
- 具体的な棄却理由、再検証条件、次の有望な仮説。
- 再現可能な成果物・データ/コード/設定ハッシュ、開発上のバグ・Holdout露出情報。

旧quant-btc-labで「Entry探索だけのGAなのに決済も十分調べた」と誤解しないため、探索対象の範囲と未探索部品を明示する。

## 5. 初期MVPでも削らない品質とUX

**品質・制御**：
- LLM生成のStrategySpec/ルールと、共通の会計/約定/コスト・評価処理を分離。
- 未来データ参照を拒否し、同じ合成fixtureで結果を再現し、取引コストは基準/好条件/ストレスを区別。
- 事前ベンチマーク、試行系譜・選抜履歴、最低限のHoldout/partition利用記録と汚染状態を保存。
- 研究予算と権限境界を強制。料金・利用規約・境界未確認なら該当外部処理を停止する。
- 実売買、口座認証、外部発注は禁止。

**最小Cockpit**：`仮説 / 現在フェーズ / 担当 / 次バックテストまでの残工程 / Runnerの実稼働状態 / 完了・無効・失敗 / 次アクション / ユーザー要対応 / レポートへのリンク`。見た目の洗練度は後回し。進捗はAI自己申告ではなく状態イベントと成果物で判定。

**受け入れテスト**：要件の全42テストを捨てず、StageごとのGateに配分。Stage 1Aの代表的な縦断受け入れケースを10〜15件に絞り、上位の安全/科学不変条件は省略しない。テスト件数の削減自体を目的にしない。

## 6. データ・費用の設計

最初は暗号資産現物の単一venue・pair・timeframeと実際に検証可能なデータ粒度に限定。OHLCVだけで板・tick順序・intrabarの損切り/部分決済を正確に再現したと主張しない。市場・venue・feed・時間足は未決であり、本書では決めない。

月3,000円は**追加従量支出の制御目標**。それで研究に必要な有料feedの品質が達成できるという保証ではない。発注可能性、データ権利、費用が不明なら、有料取得やRunnerを始めない。予算内のデータのみを使うために研究品質を偽装せず、必要なら研究対象を縮小・保留する。

既存のWindows 11、`asteriade.exe`、実行時Node/npm/Docker/別DBサーバー不要というユーザー向け制約は維持。Go/SQLite/Codex Adapter/Bedrock/具体的sandbox手段は現時点の実装・技術選択としてARCHITECTUREに記し、より良い手段への変更はユーザー向け制約・費用・移行・検証を満たす場合だけ提案する。

## 7. 継続・縮小・撤退のチェックポイント

「優位性を見つけられないから直ちに開発中止」も「研究できる限り無期限拡張」も避ける。

- **Stage 0B完了時**：自作部分の妥当性、OSS/旧コード再利用、最初の動くMVPまでの未解決工数を見積もる。複雑な再実装が必須ならscope変更。
- **Stage 1Aの最初の完走時**：人工データで機械的な正しさ、別の研究者が再現できるか、ユーザーが逐次「続きを」と指示しなかったか、進捗が理解できたかを検証。
- **Stage 1Aで数サイクル後**：無効実験比率、重複した仮説、手動対応時間、追加費用、Market Knowledgeの価値を確認。既存のPython＋AIより改善が見られないなら自律機能を縮小し、研究支援ツールとして残す選択を検討。
- **Stage 1B後**：ReviewerがB方式に比べ欠陥を減らすか、費用対効果があるかを記録。有用性が確認できなければReviewerを常時起動しない。
- 時間や費用の上限はユーザーの生活・開発余力を確認して定める。機械的に「何か月で利益ゼロだから中止」としない。

判断履歴、当初の目的、撤退・縮小の基準と理由をMarkdown/JSONに残し、後続AIが再評価できるようにする。
