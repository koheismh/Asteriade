## 0. この文書の使い方と決定区分

本文中の **MUST（必須）** は製品の守るべき性質、**SHOULD（推奨）** は初期方針、**DEFER（後段）** は初回リリースの対象外を示す。モデル名、API、金融商品のルールなど外部依存事項は実装時に現行の提供条件を検証し、未確認の機能を「利用可能」と表示してはならない。

本書は議論の統合案であって、AIの設計判断だけで実装、課金、公開、外部送信または取引を承認するものではない。既存の汎用AIオーケストレーション v1.1 と衝突する部分については、**投資研究への方向転換を正式承認した後に**後継要件として採用する。承認前はドラフトのまま管理する。

## 1. 目的・価値・非目的

### 1.1 目的

ユーザーが大まかな研究目標を指定すると、Asteriadeは研究テーマを選び、反証可能な仮説を立て、複数AIで批判と反論を交わし、計画を凍結してCodex等に実験を実装・実行させる。結果を機械的に評価し、有意な失敗や残された課題も蓄積しながら、予算・期限・権限の範囲内で次の研究を進める。

- 「利益が出るまでパラメータを変え続ける」システムにはしない。
- **不採用・不確実・再現不可**も有効な研究結果として保存する。
- 予測効果の発見、取引ルールへの変換、決済と資金配分、実運用可能性の評価を混同しない。
- 利益の大きさだけでなく、研究結果の証拠の強さと将来への一般化可能性を別々に扱う。
- ユーザーがAI会話を読まなくても「何の仮説か」「何が終わったか」「次は何か」を把握できるようにする。

### 1.2 設計原則

1. **Research-first**：UIも主要な機能も投資研究を中心に設計する。
2. **Manager-led, independently challenged**：高能力のManagerが責任を持って判断し、Reviewerは独立して反証する。
3. **Evidence over assertion**：AIが「完了」「有望」と言うだけでは成果として扱わない。
4. **Science gates vs risk appetite**：未来情報混入などの検証不備は厳格に排除する一方、リスク許容度は固定の保守基準を強制せず設定可能にする。
5. **Bounded autonomy**：討論・再試行・研究回数・期間・課金を必ず有限にする。
6. **Reproducible and portable**：別のAIやツールが研究を引き継げる証拠を残す。
7. **Fail closed**：権限、料金、Runnerの安全性、データ境界が判定不能なら危険な実行を止める。

### 1.3 非目的（初期）

- 発注、リアルマネー運用、取引所アカウント連携、秘密鍵操作、注文自動化。
- 「利益を保証する」「常に勝てる戦略を発見する」という製品表現。
- 一般的なWeb業務、資料作成、ソフトウェア開発のための汎用エージェント製品化。
- 多市場・多数プロジェクト・クラウドRunnerの完全な同時運用をMVP成立条件にすること。
- ブローカーや取引所での実約定を、OHLCVのみのバックテストで完全再現したと主張すること。

## 2. ユーザー体験・利用モード

### 2.1 Research Project

Projectは研究目的、対象市場、使用可能なデータ、投資方針、AIチーム、研究予算、検証の境界、成果物のまとまり。複数Projectを保存でき、同時実行数は設定可能。初期は**一つの活動中Project + 内部で複数Reviewer/Runner**を主利用形態とする。

### 2.2 研究の開始方法

- **自律探索モード**：市場や目標を指定し、研究テーマ・時間足・仮説候補をManagerが提案・選択する。自律選択の許可された市場範囲を超えてはならない。
- **テーマ指定モード**：ユーザーが市場、時間足、現象、売買方向、実験課題などを指定して始める。
- **既存研究の再開**：過去の仮説・報告書・失敗理由・未検証項目から次のサイクルを起こす。
- **計画確認モード**：各研究計画や重要な方法変更を人間が承認してから実行。**自動研究モード**でも予算・実行権限・最終Holdout・外部送信等の必要な制約を免除しない。

既定は高い自律性を保ち、研究上の可逆的な通常判断はManagerに任せる。対象市場を跨ぐ方針転換や研究条件の拡張は、Projectが設定した許可範囲内に限定する。

### 2.3 代表的な利用の流れ

`研究テーマ発見 → 仮説登録 → Reviewerとの討論 → Manager最終判断 → 実験計画凍結 → 実装・事前テスト → バックテスト → 機械的な結果評価 → AIによる考察 → レポート保存 → 次の研究`。

各段階は永続化された状態遷移であり、アプリ再起動後も現在位置と次の実行可能な操作が分かること。

## 3. AIチームと討論プロトコル

### 3.1 役割

| 役割 | 最小責務 | 推奨モデル方針 |
|---|---|---|
| Research Manager | 仮説、計画、反論への回答、最終判断、次サイクルの方針 | 利用可能な高能力Codexモデルを優先 |
| Logic / Market Reviewer | 因果説明・市場構造・競合理論の批判 | Bedrock等の許可済み低コストモデル |
| Statistics / Validation Reviewer | 標本、検定、時系列分割、多重探索、リーク、過学習を監査 | 許可済みモデル＋機械的チェック |
| Cost / Execution / Risk Reviewer | 手数料、スプレッド、約定可能性、テール損失を批判 | 許可済みモデル |
| Opportunity / Coverage Reviewer | 不当に厳しい棄却、未検証のエントリー・決済・資金管理を指摘 | 許可済みモデル |
| Experiment Engineer | Codexで検証機能を実装・修正し、実験Runnerを実行 | 利用可能なら軽量Codexサブエージェント、難所は高能力モデル |

役割は固定された**責務**であり、常駐するAIプロセスではない。初期版では複数観点を少数Reviewerへ統合可能。ただし「必須の統計レビューが省略されたのに実験が進む」ような無言の縮退は不可。指定Reviewerが使用できなければ、事前許可済みの代替に切り替えるか`blocked_review`で停止する。

### 3.2 有限の5ステップ討論

1. **Manager提示**：仮説、なぜ効くか、対象市場、期待される観測、代替説明、実験計画、合否基準。
2. **Reviewer独立反論**：互いの意見とManagerへの迎合を避けて、具体的な懸念・反証方法・改善案を提示。反論がなければその旨を明記してよい。
3. **Manager回答**：各指摘を`採用 / 一部採用 / 却下 / 実験で確認`に分類し、正しい指摘を認め、異論には根拠を示して反論する。
4. **Reviewer再反論**：Manager回答を受けた重要な未解決点について**最大1回**再反論。新しい材料がなければ省略可。
5. **Manager最終判断**：`実験へ / 計画修正 / 対照実験 / 保留 / 棄却`を確定し、全指摘への対応、採否理由、次の具体的行動を保存。

- **最大2回のReviewer発言機会**をオーケストレーターが制御する。議論の再帰呼び出し、Reviewer同士の延々とした会話、全員一致待ちはしない。
- 論点に決着がつかなければ、観測で区別できる代替仮説を実験化するか、未解決として保留する。
- 同じ反論の再掲、新しい証拠のない微修正の反復を検出し、再会話ではなく記録・次の検証へ移行する。
- Managerに判断権はあるが、**データ漏洩、検証欠陥、アクセス制御、費用・外部操作の強制ゲートは上書き不可**。
- Manager最終回答が空・不正な構造化出力・期限超過の場合は、決定済みと見なさず`needs_attention`にする。再試行回数は有限。

### 3.3 討論品質と学習

論点ID、指摘内容、反論内容、採否理由、関連実験ID、後日の観測結果を紐付ける。どの指摘が有益だったかを振り返るが、**Reviewerの自信や発話量だけで評価しない**。失敗結果を都合よく読み替えてモデル評価に転用しない。

## 4. 自律研究サイクルと状態管理

### 4.1 概念データモデル

`Project → ResearchProgram → Hypothesis → ResearchCycle → Experiment → ExperimentRun`。AIの役割定義`AgentRole`、具体的な会話`Session`、実行`Execution`、決定`Decision`、反論`ReviewIssue`、出力`Artifact`、データの区分`DatasetPartition`を別に管理する。

- `Hypothesis`：観測可能な市場現象、予測内容、根拠、反証条件、関連する既知の仮説。
- `ResearchCycle`：ある仮説に関する討論・実験計画・判定・派生研究への遷移。
- `Experiment`：固定された研究計画と変動可能な試行パラメータ空間。
- `ExperimentRun`：特定データ・コード・乱数seed・設定の実行試行。再実行のたびIDを付与。
- `Decision`：採否、改訂、予算追加、研究方向転換の根拠と代替案。

### 4.2 状態

Project: `draft / planning / researching / paused / needs_attention / finished / failed / cancelled`。

Cycle: `hypothesis / first_review / manager_response / rebuttal / decision / experiment_design / preflight / running / validating / interpreting / reported / deferred / rejected / blocked`。

Run: `queued / preparing / running / succeeded / failed / interrupted / outcome_unknown`。

**Runnerがsucceededでも実験がvalidatedとは限らない**。実験出力、データ品質、検証エンジンの検査を通ったときだけ「バックテスト完了・有効な結果」とする。さらに科学的に優位性が確認できたかどうかは別の判定。

### 4.3 ループと停止条件

- 討論は最大2ラウンド。ResearchCycle・ExperimentRun・再試行・壁時計・稼働時間・金銭の上限を管理する。
- 初期値案（調整可能）：連続自律サイクル最大5、同仮説の大きな再設計1回、証拠増加のない連続2サイクルで方向性再検討。これは**製品の暫定初期値であり普遍的研究基準ではない**。
- 繰り返し判定は自然言語類似度だけでなく、仮説の市場・対象・条件・試行済みパラメータの構造化IDで行う。
- 予算が残っている場合でも、有意味な新しい研究課題がなければ「研究プログラムを保留」としてよい。無意味に新たな検証を作らない。
- クラッシュ後に同じ外部操作や課金実行を二重起動しない。永続化したIDとcheckpointから再開し、`outcome_unknown`を確認する。

## 5. 市場データと取り扱い

### 5.1 共通データ要件

- Rawデータ（取得元レスポンス）を保管し、正規化データ、Feature、検証用の分割データを別に管理する。
- タイムゾーン、バー開始/終了、**実際に情報を利用できた時刻**、確定足、取引時間、祝日、欠損、重複、修正履歴、通貨/契約単位を記録する。
- データ源、取得日時、ライセンス・再配布可否、対象銘柄、範囲、解像度、欠損率、checksum、既知のバイアスを保存する。
- APIの失敗を無言で「市場データ欠損」に置き換えない。価格の無断補完・未来時点からの逆算をしない。
- 取得APIやプロバイダーに料金がある場合、予算と利用規約を確認。データを自動でGitHubの公開リポジトリにアップロードしない。

### 5.2 市場別のアダプター

| 市場 | 特に必要な取り扱い |
|---|---|
| 暗号資産 | 24時間365日、現物/デリバティブ区別、取引所、maker/taker、流動性、funding、取引停止、ペア通貨 |
| FX | 通貨ペア、bid/ask、取引セッションと週末、経済指標時のギャップ、スワップ、ブローカー仕様 |
| 日経225mini | 大阪取引所のセッション、祝日、呼値、契約倍率、証拠金、限月・SQ・ロール、日中/夜間連続性 |

標準バックテストインターフェースは共通でも、**全市場に同一の費用・会計・時間規則を固定しない**。履歴データを入手できない市場/時間足は、利用可能になったかのように表示しない。

## 6. 仮説探索と最適化（GAを含む）

### 6.1 仮説の出所

市場メカニズム、公開研究、特徴量からの探索、既存仮説への反論、失敗の原因、異なる市場環境、コスト差、執行方式の改善などから候補を作る。テクニカル指標の無差別な組合せだけに限定しない。

### 6.2 Strategy Components

検証可能な範囲で `Signal / Entry / Exit / Position / Sizing / Risk / Execution` を分離し、各成分の依存条件と探索カバレッジを追跡する。

研究レポートには最低限、**検証した項目・未検証項目・検証しなかった理由**を残す。例：単発/分割エントリー、固定決済/トレーリング/部分決済/期限決済、建玉併存、損失制限、ロング/ショート、時間帯/相場環境。

### 6.3 探索手段

- 探索なし（事前に規定した仮説の直接比較）、Grid、Random、必要に応じてGAを選べる。
- **GAは専用の実験ツール**。Managerが使用理由を示して選択し、Asteriadeが統一されたRun・結果・予算・データ境界を管理する。
- GAの遺伝子表現に含めた要素と**含めていない要素を明示**する。EntryだけのGAを全取引ルールの最適化と呼ばない。
- Objectiveは過去利益だけに依存させず、費用控除後の経済性、期間安定性、複雑さ、標本不足、多重探索を考慮する。複数目的・Pareto候補も後段の選択肢。
- seed、個体数、世代数、変異・交叉、探索可能な全空間、評価済みの全候補/キャッシュIDと停止条件を記録。
- 少数パラメータでは単純な探索を優先し、効果の原因が不明な巨大GAから始めない。
- 選抜と独立評価を分ける。最終Holdoutや外側OOSをGAの探索フィードバックに使わない。

## 7. バックテストエンジンと執行・会計

### 7.1 コア機能

- オーダーイベント、建玉、約定、手数料、現金、含み損益、実現損益、必要証拠金、強制決済、ロング・ショートを共通イベントとして記録。
- 分割エントリー、追加建玉、部分利確、トレーリングストップ、決済順序、複数建玉、レバレッジを**市場・商品の表現能力に応じて**シミュレーション可能とする。
- OHLC足の高値・安値への到達順序が不明なら、有利な到達順序を勝手に仮定しない。約定ルールを固定し、保守的比較または細粒度データを要求。
- バー時計と情報利用可能時刻を強制し、未来足・取引終了後のデータ・後日の改訂を過去時点に混入させない。
- シミュレーションと観測データ・ストレス条件を明確に表示し、ブローカー・取引所の実運用と同等とは主張しない。

### 7.2 コストシナリオ

同じ戦略について、以下を**分離して**評価する。

1. 実行可能な楽観ケース（手数料・最良条件を現実に照らし合わせる）。
2. **根拠のある基準ケース**（通常の市場状態、注文規模、注文方法を反映）。
3. ストレスケース（急変・低流動性・スプレッド拡大・滑り）。

費用を`明示手数料 / bid-ask / slippage / market impact / funding・swap / rollover`等に分解し、全取引に一律の「最悪ケース」を適用した結果だけで棄却しない。費用分布が不明な場合は「推定不能・仮定依存」を表示し、楽観側の好成績を独立した成立証拠にしない。急変で売買シグナルと費用が同時に悪化するリスクを検証する。

### 7.3 高リスク・高リターンの評価

- Projectごとに研究用のリスク方針を設定可能：高成長志向、安定志向、カスタム。
- 投資枠全損、単発の極端な損失、連続試行、資金配分、資金枠を超える損失可能性を分析し、**期待利益だけでなく損益分布・推定不確実性**を比較する。
- 大きなDDだけで有望な研究を自動破棄しない。一方「高い利益が期待できる」というAIの主張だけで極端なリスクを正当化しない。
- 資金枠を越える損失の許容について設定できても、**ギャップ・追証・取引所清算などで損失を設定内に確実に止められるとは保証しない**。破産状態と債務発生を別の事象として記録。
- `取引の優位性`と`ポジションサイズ・レバレッジでの利益拡大`を分けて比較する。
- 個別の資金量、資産額、リスク許容数値はローカル非公開設定で扱い、公開GitHub文書・ログへ自動掲載しない。

## 8. 統計検証と研究データの保護

### 8.1 検証の三層

- **Development**：仮説立案・探索・パラメータ比較。
- **Validation / Walk-forward**：時系列に沿った候補評価、近傍感度、別期間・環境での検証。探索への再流入は記録し、選抜バイアスを考慮する。
- **Final Holdout / Prospective**：選抜と実装の凍結後に行う、原則として独立した最終評価。結果を繰り返し見て条件変更したら未使用状態へ戻さない。

時間の流れ、ラベル期間の重複、purging/embargo、複数検定、試行回数、データ品質、ルックアヘッド検査、パラメータ感度を評価する。統計的に有意な価格変動の偏りと、費用控除後に実現可能な戦略利益を別々に記録する。

### 8.2 Holdoutのアクセス記録と不具合処理

- Finalデータの値を研究AI/GAに自由に閲覧させない。テスト開始、値アクセス、結果公開、コード修正、再実行要求の監査記録を残す。
- バグ発見時に「1年待つ」ことを機械的な唯一の解決策としない。**何が見られたか、何が変更されたか、科学結果に影響するか**を調査する。
- 出力を変えないインフラ再試行と、計算結果を変える科学的なバグ修正と、結果に合わせた戦略変更を区別する。
- 修正後の再評価が可能でも、**未使用データとしての独立性を取り戻したと誤表示しない**。必要なら`corrected reanalysis`、`contaminated`、`inconclusive`、`prospective pending`として保存。
- データ状態例：`unseen / preflight / evaluation_active / inspected / defect_review / consumed / corrected_analysis / retired`。状態の巻き戻しは単なるGit/会話履歴操作では不可能。
- 最終結果に結びつくコード/データ/ルールのhashを記録し、修正後は別の実験identityとする。
- 未使用の適切な別期間がない場合でも、**Developmentの研究は継続可能**。ただし独立最終評価が未完了という状態を維持する。

### 8.3 コードと実験の品質保証

最終Holdoutの前に、実市場の最終データではなく人工データと既知の期待値によって、損益、約定順序、コスト、分割決済、建玉、タイムゾーン、欠損、証拠金、ロール、再現性などのテストを実施。修正したバグの再発を防ぐ回帰テストを追加する。

**検証エンジンが壊れている場合は、どんなに好成績でも科学的に採用できない**。必要なテストが未完了なら自動昇格を拒否する。

## 9. 評価指標と研究の採否

共通の最低出力：Gross / Net return、費用内訳、取引件数、保有期間、勝率、損益比、最大DD、Sharpe等のリスク調整指標、期間別成績、worst-fold、感度、ロング/ショート、リスクのテール、資金枠超過シナリオ、サンプル数、推定誤差。

- `実装が正しいか`、`効果が頑健か`、`基準コストで経済性があるか`、`ストレス時に何が起こるか`、`利用者の研究方針に合うか`を**別の判定軸**とする。
- 区分例：`invalid / insufficient_evidence / rejected / promising_needs_validation / high_risk_candidate / execution_improvement_candidate / validated_research_result`。
- 高リスク候補という状態は将来利益の認定ではなく、追加研究に値するという意味。
- 「好成績であれば必ず取引」とはしない。初期システムに実売買機能を持たせない。
- 研究テーマを広げる際にはデータスヌーピング・重複検定の増加を追跡し、最終確認の役割を侵食しない。

## 10. Research Cockpit：進捗の見える化

### 10.1 画面に常に出す情報

ユーザーが画面を開いて**チャット履歴を読まずに**分かることを受け入れ条件とする。

1. 今検証している仮説のタイトル、自然言語の説明、対象市場/銘柄/時間軸/方向。
2. 現在のProject/ResearchCycle/Experimentと現在フェーズ。
3. **次のバックテストまでに残る具体的ステップ**（討論回答、再反論、Manager判断、実験凍結など）。
4. 実際にバックテストRunnerが稼働しているか。`開始前 / 実行中 / 終了・検証中 / 完了 / 無効 / 停止`を区別。
5. 最新の結果・不採用理由・次の実験・ユーザーによる操作が必要か。
6. モデル、Coder/Runner、費用、最終更新時刻と待機/停止理由。

### 10.2 UI基本方針

- ダークグラファイト調のプレミアムなResearch Cockpit。左にProject一覧（暗号資産、FX、日経225mini等）、メインに活動中の研究を表示。
- 「何体のエージェントが稼働したか」より**研究の状況と発見**を優先。
- 議論を`1 Manager仮説 / 2 Reviewer独立反論 / 3 Manager回答 / 4 Reviewer再反論 / 5 Manager決定`として表示し、完了済みと残り段階を示す。再反論省略も正しく反映。
- バックテスト中は開始時刻、実Runnerの状態、処理済みのジョブ/試行、前回heartbeat、進行不能の理由を表示。根拠のない百分率や終了時間を捏造しない。
- `バックテスト完了・結果解析中`を`バックテスト実行中`と混同しない。
- 重要なレビュー論点、Runnerログ、詳細な研究履歴は必要なとき展開。Usage & credits画面は簡素にする。
- 「Next Action」には、自動で次に何を行うか、ユーザー操作の有無を明示する。
- 全進捗は**AIの自己申告ではなく、イベント/実行状態/成果物検証結果**を根拠とする。

### 10.3 通知

ユーザーへの通知は原則、研究セッション/親Projectの区切り、重要な結果、承認要求、質問、予算警告、重大な停止・検証欠陥。Reviewerの個別発話や子タスク完了を逐一プッシュしない。アプリ内では詳細な進捗をいつでも閲覧できる。

## 11. モデル・Codex・Bedrockの利用とルーティング

- Windowsローカル初期実装はCodexの**公式にサポートされる接続手段（例：App Server）**を優先。ChatGPT契約の利用資格・クォータ・クレジットを確認し、無断で別の有料APIへ切り替えない。
- Managerは利用可能な高能力モデルを優先。レビュアーはAWS BedrockのConverse/ConverseStream対応モデルを候補とし、モデルごとの価格、リージョン、機能、認証・ツール対応を確認する。特定国/系列のモデルも適格性・評価結果と費用で選べるが固定保証しない。
- Experiment EngineerはCodexに委譲。軽量Codexサブエージェント（例：Luna）は、**実際に利用可能と確認できた場合のみ**狭い検証/実装へ使用。
- 非AIルールエンジンがRunner能力、OS、権限、予算、認証、機能を先に照合し、不適格候補を除外。残りを速度/費用/品質で選択。曖昧な依頼の分類にAIを使う場合も強制ゲートを迂回しない。
- 役割別のプロンプト・モデル設定・バージョン・入力要約を保存。レビュアーの独立性を保ち、当初レビューに他Reviewerの回答を渡さない。
- Bedrock等では会話状態の保持をAsteriadeが明示的に管理。モデルの会話継続可能性や能力を推測しない。
- Kiro CLIは利用条件上の正当性が確認されるまで自動連携対象外。

## 12. 追加費用・利用枠

- ユーザー既存のサブスクリプション料金とは区別して、追加従量課金の**初期上限は月額3,000円**を目標（既存 v1.1 から継続）。80%到達時に警告。
- モデル別、研究Project別、Experiment別、請求確定/推計/予約額を表示。月額上限・不明料金・利用枠の超過が見込まれれば新たな従量課金を停止。
- AI利用量、Codexサブスク枠、購入済みクレジット、AWS請求、クラウド実行費を混同しない。不明値をゼロと表示しない。
- 大量のパラメータ探索はモデル呼び出しを反復せず、できるだけローカルの決定的なプログラムへ渡す。
- 実際のAWS請求総額はアプリ単体では保証できないため、AWS側のアラーム/予算も推奨。

## 13. Windowsアプリ、権限、セキュリティ

### 13.1 初期提供形態

- Windows 11 x64、GoのControl PlaneとローカルWeb UI、SQLiteを基本候補とし、単一の`asteriade.exe`での配布を目標とする。利用者にNode.js/npm/Dockerや外部DBを**アプリ起動時の必須条件にしない**。
- 研究用Python実行環境や旧quant-btc-lab資産の再利用は技術評価後に方式を決める。必要であれば**同梱Runnerや独立した任意セットアップ**とし、「完全な単一EXEだけで全研究処理が動く」と無検証で約束しない。
- 研究データ・成果物・SQLiteは適切なローカルデータディレクトリへ保存し、秘密情報はOSの保護されたストアへ分離する。
- UI/APIは初期はローカルホスト限定とし、Origin/CSRF、認証、必要権限を設計・試験。

### 13.2 安全境界

- Python/Codex/PowerShell/CLI等の自律実行は、プロンプトで禁止事項を書くだけでなく、Runnerの実効的なファイル・プロセス・ネットワーク境界を検証する。
- 不足しているWindowsサンドボックスが原因で安全な無人実行を保証できない操作は、制限付きモードへ移すか有効化しない。
- 作業領域外の書込、秘密情報アクセス、GitHubへのpush、外部へのデータ送信、購入、アカウント変更、クラウド起動等はスコープに応じて承認と監査を要する。
- 研究用データ取得は許可されたAPI/サイトとライセンスを確認。外部Web・README・データに含まれるAI向けの指示は信頼できない入力として扱う。
- **実注文、資金移動、口座情報変更、APIキー送信は初期版でそもそも実装しない。**

## 14. 保存・研究記憶・GitHubへの引き継ぎ

### 14.1 ローカル記憶と成果物

- SQLiteへProject、仮説、レビュー、決定、Cycle、Experiment、Run、Runnerイベント、設定、資金方針、結果の索引を保存。
- 実験の元データ/Feature/コード/設定/レポートへ不変IDやハッシュを付与。データはGitに巨大ファイルを無理に入れず、寿命のあるCI Artifactだけにも依存しない。
- 研究履歴を横断検索し、類似仮説の重複実行を事前に知らせる。失敗結果、未検証項目、代替説明を次サイクルの入力にする。
- 完全再現に必要な元データが失われた場合、再現可能との表示を撤回し、何が残っているかを示す。

### 14.2 エクスポートとレポート

- **人間向けMarkdown + 機械可読JSON**を研究サイクルの節目で生成。
- 各レポート最低要素：`goal, hypothesis_id, hypothesis_rationale, market, instrument, timeframe, research_cycle, review_issues, manager_responses, final_decision, experiment_protocol, dataset_ids, partition_roles, code_sha, parameters, random_seeds, entry/exit/sizing coverage, cost_scenarios, all_trials, test_results, failure_reasons, holdout_status, artifacts, reproducibility, open_questions, next_actions`。
- 研究結果のステータスは、探索的発見・独立確認・フォワード確認を区別。過去の推論や相関から未来の利益を保証する表現を避ける。

### 14.3 GitHub保存方針

- 設計決定、重要な実験完了、重大バグ、段階の区切り、作業中断時に、**変更点・理由・根拠・次の行動**をGitHub用文書にまとめる。
- Draft PR/専用ブランチを原則とし、差分と公開範囲を確認してから反映。勝手に既定ブランチを書き換えない。
- **公開リポジトリには個人の投資額・口座情報・認証情報・非公開市場データ・API秘密を送らない。** GitHubアップロードは送信対象・許可スコープの事前確認を必要とし、アプリの新機能として自動同期を実装する場合も明示許可が必要。
- 次のAIが読む`HANDOFF.md`に、製品の現在地、確定事項、保留、次の具体的手順、制約、関連Artifact URIと保全状態を明記。
- チャット履歴の全文を強制共有しない。GitHub保存済みでも、内容に不整合があれば人間に判断を求める。

## 15. 管理・エラー・通知・回復

- アプリ停止・PC再起動から、研究状態、討論ラウンド、ランダムseed、実験checkpoint、費用予約を復旧できる。
- Runnerが行った外部操作の結果が不明なら`outcome_unknown`で止め、無条件再送しない。
- 一時停止（新規実行停止）、中断要求（進行中Runnerへの停止要求）、キャンセル（研究プログラム停止）を分ける。
- 計画の変更・レビューの新たな論点・実験の棄却をイベントで記録。自動研究が進まない場合は「次の作業」ではなく「停止理由と解除条件」を明示する。
- 予算超過、データ整合性違反、実装バグ、権限違反時は黙って続けず明示的な要対応状態へ遷移する。

## 16. 実装優先順位とマイルストーン

| 段階 | 範囲 | 次段階へ進む条件 |
|---|---|---|
| **Stage 0 — 信頼できる基盤** | Windows起動、永続化、Runner安全境界、テスト用人工データ、最小の市場データAdapter、共通会計/検証 | 安全な起動と再開、既知の損益・リーク・約定テスト合格。データ取得と再現が可能 |
| **Stage 1 — 1市場の研究MVP** | 1市場で仮説・有限のAI討論・Manager判断・Codex検証・結果・Research Cockpit・Markdown/JSON出力 | 仮説から報告まで手動会話の「続けて」を必要とせず完走し、進捗と結果の根拠が見える |
| **Stage 2 — 自律研究の品質向上** | 研究記憶、研究テーマ発見、探索カバレッジ、Grid/Random、GAの選択利用、包括的なOOS/結果検証、予算制御 | 未検証項目と負例を含めて自律研究を繰り返せ、適応的過学習の境界を維持 |
| **Stage 3 — 市場拡張と運用性** | FX、日経225mini、商品別約定/限月、データ管理、レポート高度化、GitHub引き継ぎUX | 市場固有の会計テストと再現性が合格し、複数Projectの研究が混線しない |
| **Future** | EC2 Runner、モバイル閲覧/通知、実取引連携の可否検討 | 明示的な新規要件・リスク審査とユーザー承認が必要 |

**原則：** Stage 0/1にも最小のデータ隔離、費用上限、権限制御、報告が必要。GAや多市場UIの完成を待たずに信頼できる1本の研究ループを成立させる。旧プロジェクトから既存Python検証コードを流用できるかは試験して決定する。

## 18. 変更点（旧v1.1との差分）

1. **初期製品の対象を汎用AIオーケストレーションから投資検証・研究へ変更**。一般的な開発タスクUIは先送り。
2. 中心概念に`Hypothesis / ResearchCycle / Experiment`を追加し、ユーザー画面の主役を研究の進捗と結果にする。
3. **高能力Managerによる最終決定 + 独立Reviewerの初回反論 + Manager回答 + 必要な再反論**を有限回で実施。
4. Codexは検証コードの実装、Bedrock等は独立Reviewerの候補。ルールエンジンが可用性・権限・料金を管理。
5. GAを自律研究全体の中心ではなく、**必要なときに利用する探索ツール**として位置付ける。
6. EntryだけでなくExit/分割建玉/Risk/Sizingの研究カバレッジを記録する。
7. コスト評価を一律の極端な悲観値から、根拠のある通常・好条件・ストレスの複数シナリオへ拡張。
8. 高リスクを許容する研究目的を認め、DDの機械的な保守一律判定をやめる。ただし検証の正しさは厳格に担保。
9. Final Holdoutの露出、計算バグ、再分析の科学的な位置付けを明示し、安易な「データを捨てて1年待つ」を固定ルールにしない。
10. 討論・実装・バックテスト・分析の現在位置と残ステップをユーザーに**自動で可視化**。
11. 研究・失敗・反論・未探索範囲と再現性をMarkdown+JSONで蓄積し、GitHubへ定期的に引き継ぐ。
12. 既存のWindowsファースト、実効権限制御、追加課金上限、ローカル保存、結果の証拠確認は維持。
