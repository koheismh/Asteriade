## 0. プロジェクトのアイデンティティ

**Asteriade**が正式な製品名・開発プロジェクト名である。README、UIタイトル、ログ、成果物および配布名も原則としてこれを用いる。`Multi-Agent Control Center`などは説明用の一般名であり製品名として採用しない。

名称は、ギリシャ神話の星に関わる女神 **Asteria** と、迷宮から導く糸の物語の **Ariadne** をモチーフにした造語。複数AIが星々のように活動し、複雑な仕事の道筋を見失わずに完了へ導くイメージとする。商標・名称の利用可能性は別途確認する。

## 1. 目的・設計原則

ユーザーが自然言語で与えた目標を、親AIが計画・フェーズ・タスクに分解し、必要なら子AI・孫AIを起動して実行する。モデル/Runnerの選択、会話文脈、成果物、承認、予算、進捗、通知を一元管理する。

対象は**開発・Web調査・分析・資料作成など広範囲**。初期実装はWindows 11上で動作し、ユーザーのPC稼働中のみ処理を行えばよい。将来はクラウド上に管理機能を配置し、自宅PCやEC2でタスクを実行しながらスマートフォンから確認・追加指示・承認できるようにする。

### 必須の4原則

1. **Fail Closed:** 権限、認証、利用料金、実行環境の安全性を判定できない場合は実行しない。
2. **Capability-based Routing:** 必要ツール、OS、権限、認証、モデル機能を満たすRunner/モデルの組だけを選ぶ。
3. **Evidence-based Completion:** モデルの「完了しました」という発言だけでは成功扱いにしない。成果物・自動テスト・客観的根拠に基づき検証する。
4. **Graceful Degradation:** あるプロバイダーが利用不能でも、許された他機能を維持する。ただし無断で従量課金先へ切り替えない。

追加原則：**Control PlaneとRunnerの論理分離、説明可能なモデル選択、最小権限、追跡可能な状態遷移、コンパクトなUI、ユーザーへの通知の最小化**。

## 3. 用語とドメインモデル

| 概念 | 定義 | 重要な関係 |
|---|---|---|
| `Project` | ユーザーの目標・設定・最終成果物を束ねる単位 | 多数のAgent/Plan/Taskを持つ |
| `Agent` | 計画・判断・実行を担当する論理的な役割（親/子/孫） | 親Agent IDを保持でき、固定モデルを前提としない |
| `Plan` / `Phase` | 目標の段階的実行計画 / 進捗単位 | 計画は版管理。フェーズはTaskに紐付く |
| `Task` | 目的・依存・権限・完了条件を持つ**仕事そのもの** | 所属Project、担当Agent、任意の親Taskを持つ |
| `Execution` | 特定Taskに対する**1回の実行試行** | 利用Runner、プロバイダー/モデル、開始/終了、結果、コストを固定して記録 |
| `Session` | モデル・接続方式に固有の会話/作業文脈 | Agent/Executionと関連。異なるモデル間で暗黙共有しない |
| `Runner` | 実際にツール・CLI・作業領域を提供する実行環境 | OS、権限、ツール、接続状態を公開 |
| `Artifact` | ファイル、レポート、Git差分など検証可能な成果物 | Task/Executionと紐付く |
| `Instruction` | ユーザーの新規指示・修正指示 | 受付と適用を独立して管理 |

**不変条件：** TaskのIDは再試行・モデル変更でも不変。再試行ごとにExecution IDを新規発行する。Session IDはプロバイダーのセッションと混同しない。子AI完了通知と最上位Project完了通知は異なるイベントとする。

### 概念関係

```text
Project -- Plan(version) -- Phase -- Task -- Execution -- Session
    |                              |          |
    +-- Agent(root) -- Agent(child) +          +-- Runner / Provider / Model
    +-- Artifact / Notification / Approval / Budget / Instruction
```

## 4. Windows技術・配布・初期セットアップ

- OS: Windows 11 x64。**アプリ本体**を単一の `asteriade.exe` として配布する。実行時にnpm/Node.js/Docker/外部DBサーバーを要求しない。
- Go製バックエンド、静的フロントエンドをEXEへ埋め込み、SQLite（WAL）をユーザーのローカルアプリデータ領域に保存する。ビルド時のnpm等は許容。
- 外部CLI/Edge等のインストールはEXEの単体配布条件の例外。未導入の場合はセットアップ画面で明確に案内する。
- アプリは既定ブラウザを起動し、ローカル管理APIを `127.0.0.1` に限定して公開。UIとAPIは同じOriginを原則とし、Origin/CSRF保護やセッション・ローカルトークン対策を実施する。
- 初回セットアップは**接続診断ウィザード**。Codex、Bedrock、Kiro（未対応理由表示）の認証・接続・利用可能性を別々に示す。**Codexだけで開始可能**。全プロバイダーの設定を強制しない。
- モデル一覧への掲載は使用可能の保証ではない。検証用の小さな実行を伴う接続テストでモデル利用可能性を判定する。
- 秘密情報はWindowsの保護された認証情報保管を利用。認証が未設定・失効の場合は該当Providerを停止し、他の機能は続行できるようにする。
- Windowsデスクトップ通知はアプリ識別・通知登録の実現方式を検証し、未対応時はアプリ内通知をフォールバックとする。

## 5. セキュリティ・権限強制（**Stage 0最優先**）

### 5.1 権限チェックとサンドボックス

ポリシーを定義するだけでは不十分。AIが実際に動かすCLI、PowerShell、外部ツール、ブラウザ、MCP等からの操作を**実行レイヤー側の権限制限**で抑止する。Codexなど自律型CLIは独自にコマンドを実行できるため、アプリの承認UIだけですべてを捕捉できるとは仮定しない。

- Runnerごとに利用可能な実効サンドボックス（OS権限、ファイルシステム境界、ネットワーク権限、プロセス実行権限、CLIの承認設定）を診断・検証する。
- 「作業領域外読み書き」「Git push」「任意のHTTP送信」「任意のPowerShell実行」「認証情報へのアクセス」などの**禁止操作が現実に拒否されるテスト**をStage 0で実施する。
- ネットワーク送信やプロセス起動を十分制限できないRunnerでは、外部操作を含む**無人自律実行を有効化しない**。安全な読み取り作業・レビュー等に限定するか、人間の明示的な監督下でのみ利用する。
- 実行コンテキストやプロンプトに「禁止」と書くだけの制御は不可。ローカルWindowsで強制困難ならStage 0の技術課題として明示し、最小権限の別ユーザー・隔離環境等の代替を実証してから先へ進む。
- 外部接続は許可済みの検証可能なツール経由を基本とする。未信頼Webページ・README・ツール結果の指示を上位権限に昇格させない。

### 5.2 標準ポリシー

| 操作 | 初期判定 |
|---|---|
| 指定Workspace内の通常の読み書き | 自動許可（実効的な隔離が成立する場合） |
| 指定Workspace外へのアクセス | 既定拒否。承認と安全な実行手段が揃う場合のみ例外 |
| 調査・閲覧 | 読み取り専用と**確認できる**対象だけ自動許可 |
| 外部への送信、公開、投稿、Git push、アップロード | 原則初回承認。承認後も実行直前に対象を再検証 |
| 外部データの大量削除、決済、送金、認証変更、本番デプロイ | **原則毎回承認**。自動永続許可しない |
| 操作の影響・権限が不明、サンドボックスが不十分 | **拒否・ユーザーへ説明** |

HTTP GETでも副作用を持つサービスがあるため、HTTPメソッドのみで「安全」と判断しない。ログアウト、配信解除、既読化などの副作用があり得る操作は変更操作として扱う。

### 5.3 監査と承認

- 承認前に**送信先、対象アカウント、ブランチ/ファイル、変更差分、本文、料金・影響範囲**を提示する。
- 承認は、操作を意味的に同一と判定できる識別子・対象ハッシュ・期限・スコープに紐付ける。承認後に送信内容が変われば再承認する。
- 全操作は実行予定/許可結果/実行結果をイベントとして記録する。秘密情報はマスクする。
- 自律実行中の権限境界の変更は監査し、Runnerの実効設定を再検証する。

## 6. エージェントとタスクの状態遷移・停止

### 6.1 自律実行

- 最上位Agentはユーザーの依頼からPlan/Phaseを作成する。子・孫Agentを再帰生成できるが、階層・同時実行数・タスク数の上限はエンジン側で強制する。
- 推奨初期値（変更可能）：最大**3階層**、同時**3実行**、タスク再試行**2回**、1回の実行**30分**、親Project実働**2時間**。生成タスク総数には初期上限を設定する（値は設計時確定）。
- タスク依存関係をDAGとして管理し、循環依存を拒否。子が失敗したら親が検証・再計画またはユーザーへのエスカレーションを行う。
- 承認待ちのタスクがあっても、依存しない他タスクは進める。

### 6.2 状態の意味

- Task: `queued / ready / running / awaiting_approval / awaiting_answer / verifying / completed / failed / cancelled / recovery_required`。`paused`はTaskの凍結ではなく**スケジューラの新規実行抑制**として別に表す。
- Execution: `starting / running / succeeded / failed / interrupt_requested / interrupted / outcome_unknown`。
- Project: `draft / planning / running / paused / needs_attention / completed / failed / cancelled`。
- `Execution.succeeded` と `Task.completed` は一致しない。検証成功後のみTaskを完了にする。
- 状態変更は有効な遷移のみ許可し、履歴を追記する。中途半端なDB更新で二重起動しない。

### 6.3 停止操作の定義

1. **一時停止:** スケジューラによる**新規Execution開始を止める**。実行中のExecutionは原則継続し、安全な区切りで止める。
2. **即時停止:** 実行中のExecutor/CLIへ中断を要求する。途中処理の巻き戻しは保証せず、処理結果が不明なものは `outcome_unknown` へ。
3. **キャンセル:** Project/Taskの目標を終了し、新規作業・自動再試行を止める。すでに発生した外部副作用は自動的に戻らない。
4. **再開:** 保存された状態・権限・予算・外部操作の結果を再評価し、安全な実行地点から新しいExecutionとして再開する。

**時間制限:** 実働時間（Execution稼働時間の合計）と壁時計上の経過時間を別々に表示。承認待ち、質問待ち、ユーザー起因の一時停止は**実働2時間に含めない**。任意の最大経過期限は別設定とする。

### 6.4 実行中の追加指示

- 指示はまず `received` として永続保存、親AIが適用対象と計画版を判断して `accepted / scheduled / applied / rejected` と状態更新する。
- 既定は**次の安全な区切りで反映**。実行中モデルが公式に対応する場合だけ即時介入オプションを許す。
- 受付・適用・反映後の計画変更をUIとログに表示する。同時に複数端末から指示が来た場合は版番号と冪等IDで競合を検出する。

## 7. フェーズ・進捗・完了判定

- 最初の依頼時に、目的・成果物・制約・受け入れ条件から自動的に**フェーズ計画**を作成する。簡単な依頼なら単一フェーズでもよい。
- フェーズは名称、依存、完了条件、関連Task、状態、成果物、開始/終了、計画バージョンを保持する。
- 計画を変更したら**変更前後、理由、更新日時**を残す。進捗率の変化理由も説明できるようにする。
- 進捗は「完了フェーズ数/総フェーズ数」と「実行中のフェーズ・最新活動・次の予定」を基本表示する。百分率は実測根拠のある場合のみ表示し、AIの主観値を確定値としない。

### 完了の3段階

1. **実行終了:** モデル/ツールが応答し、Executionが終了した。
2. **検証成功:** Taskの成果物と機械的な完了条件が満たされた（Taskをcompletedにできる）。
3. **ユーザー確認済み:** ユーザーが最終結果を受諾した（別フラグ）。ユーザーの確認がなくても「検証済み完了」と表示可能だが「ユーザー確認済み」と混同しない。

検証条件の例：コードはビルド/テスト/差分/指定ファイルの確認、文書は生成ファイルと要求章立て、調査は出典・範囲・納品形式の検査。検証不能な判断は「要確認/未検証」と表示する。AIの自己評価だけで成功判定しない。

親Projectが完了になるのは、必須Phaseの完了と最終成果物の検証が成功した場合のみ。検証不能・未解決項目がある場合は、限定的な結果と未完了理由を通知する。

## 8. プロバイダー接続・モデル/Runnerルーティング

| 接続先 | 方針 |
|---|---|
| **Codex** | Stage 1の主実装。公式Codex App Serverなどを利用し、認証・スレッド/ターン・イベント・承認・中断・利用量を扱う。プラン/モデルの利用可否は実際の実行成功で確認する。 |
| **Amazon Bedrock** | Stage 2でSDK/Converse(ConverseStream)連携。会話履歴とツール呼び出しループはAsteriadeが管理。AWSリージョン、モデル機能、認証、クォータ、料金を確認。 |
| **Kiro CLI** | 公式FAQの第三者製ハーネスに関する制約があるため**自動呼び出しを初期実装しない**。明確な許諾・適合方式を確認できたときにのみアダプターを検討。 |

### ルーティングの順序

1. Taskの必要能力を列挙（ファイル読書、Git、コマンド実行、ブラウザ、画像/文書、ネットワーク、必要コンテキスト等）。
2. RunnerのOS/ツール/サンドボックス/権限/ネットワーク能力を照合する。
3. 利用可能なProvider/モデルと実際の利用権限・残り枠・リージョン・ツール対応を照合する。
4. 予算とレート制限をチェックする。**不適格な組は候補から除外**する。
5. 残った候補からルールベースで選択。選択理由と候補除外理由を記録する。

**UIのモード:** `自動（節約優先）`（既定）、`自動（速度優先）`、`Codex優先`、`Bedrock優先`、`モデル固定`。いずれも権限・予算・能力判定を迂回しない。初期はルールベースでよく、成功率を利用する高度な学習ルーティングは後段階。

BedrockはモデルAPIを呼ぶだけでローカルツールが使えるわけではない。必要なツールをAsteriade側で公開し、**ツール呼び出し→ポリシー検査→実行→結果返却**のループを実装する。対応しないモデルを選択しない。

## 9. 会話・長期記憶・成果物

- `Session`はモデル/接続方式固有、`messages`は会話メッセージ/ツール要求と結果/必要な固有署名などを保存する。
- Bedrock Converse APIは自動的に会話履歴を保持しないため、**必要なメッセージをAsteriadeが次回要求へ渡す**。モデル固有の推論情報の署名やツール結果を安易に改変・消去しない。
- 長い会話は直近履歴＋要約＋重要な決定事項＋作業スナップショットを組み立てる。ただしプロバイダー固有の「過去メッセージをそのまま渡す必要がある」条件に従う。
- 異なるモデルへの切替時は、互換のないSessionを直接再利用しない。**Taskの要件と成果物、決定事項の標準化サマリー**を引き継ぐ。
- 成果物は原則ファイルとして保持し、パス・作成Execution・更新時刻・ハッシュ・検証結果を追跡する。不要なデータの長期保管期限は設定で変更できる。

## 10. 予算・利用制限

- 追加従量課金の既定上限：**月3,000円**（既契約のCodex/Kiroサブスク月額は除外）。80%（2,400円）で通知。
- 追加請求のあるプロバイダーへ新規に切り替えるときは、ユーザーの従量課金利用許可・予算上限をチェックする。サブスク枠が尽きたからといって**無断でBedrockなどへ切り替えない**。
- リクエスト前に見積りを行い、入力見込み、最大出力トークン、モデル料金、リージョン、為替・安全余裕を含む**保守的な額を予算予約**する。
- 見積不能、単価不明、残予算不足、料金表の信頼性が不足の場合は**新規の従量課金実行を止める**。完了後は実測Usageにより精算する。
- プロバイダー別・親Project別・Task別・実行回別に料金・予約額を集計。サブスクの回数/クレジットと円建て従量料金は混同しない。残量不明は「不明」。
- クォータ/レート制限到達時は待機または**事前に許可された**代替へ切替。高額になりそうな再試行を無制限に続けない。
- Windowsローカル版のアプリ予算管理だけではAWS等の**実際の請求総額を厳密に保証できない**。請求遅延、実行中課金、外部での利用、為替変動があるため、サービス側アラート/上限管理の利用も推奨する。
- 表示：現在の推定費用、予約中の額、確定/取得済み使用量、月間上限、停止理由。

## 11. ダッシュボードと基本操作

### デザイン

**最初はコンパクト、一目で全体像、必要な部分だけ展開**。落ち着いた色調、わかりやすいアイコン、簡潔なステータス、短いセグメント進捗バーを使う。色だけで状態を伝えない。PC/スマホのレスポンシブレイアウトを採用する。

### 初期表示

- サマリー: 親AI稼働数、子・孫タスク実行数、モデル別実行数、要対応件数、月間予算/消費。
- **「要対応」件数は上部に見えるように配置。** 承認・質問をクリックすると当該案件で絞り込む。ただし長い通知一覧は常時展開しない。
- 親AI一覧は**1行程度＋小さなフェーズ進捗バー**。名前、現在モデル、状態、現在フェーズ、完了フェーズ数、子タスク数を掲載。
- 行を展開するとフェーズ一覧、フェーズを展開すると個別Task/子孫Agent。ログは別画面またはさらに展開。
- 並べ替え（要対応、最終更新、実行中など）、絞り込み（状態/モデル）、検索（プロジェクト/依頼内容）を用意。
- クイック操作：詳細、追加指示、一時停止。全体の**新規実行一時停止**も提供。
- 最新活動、次の予定、最終更新時刻を表示できる（初期一覧では必要に応じて省略・ツールチップ/詳細展開）。

### 新規依頼

- **チャット入力が主導線**。ユーザーは原則目標を入力するだけ。
- 高度な設定（使用モデル、予算、階層、権限、並列数）は折りたたんで表示。
- 実行モード：`自動実行`（安全な計画は作成後に実行）、`計画確認`（計画・見積りをユーザーが確認してから開始）。どちらも高リスク操作は個別承認が必要。

### 結果画面

- 最終要約、成果物、作成場所、変更ファイルと差分、テスト/検証の結果、未解決項目、フェーズの結果を表示。
- 「成果物を開く/取得」「追加修正」「再実行」「差分確認」を用意。追加修正は元Projectに追記して計画を版管理する。

## 12. 通知（ユーザー宛てだけ）

**ユーザー向け通知対象:** 最上位Projectの最終完了、親AIからの質問、承認依頼、予算警告/上限停止、親AIの重大失敗/停止。通知元は親AIの判断または予算・承認管理エンジンとする。

**通知しない:** 子AI・孫AIの開始/終了、通常のリトライ、フェーズ完了、モデル切替、内部的な調整。これらはイベントログには残すが**ユーザーへプッシュしない**。子AIからの質問はまず親AIへ渡す。

- 通知センターはベルアイコンで開閉、未読/既読・履歴・集約・重複排除に対応。
- Windows 11のデスクトップ通知はアプリ稼働中の通知を目標とし、未対応時はアプリ内通知へフォールバック。
- 通知を開いたら**該当結果/質問回答/承認/料金/エラーの画面に直接遷移**する。
- 完了通知から成果物・検証結果・未解決事項へ到達できる。
- PC/アプリ停止中の送信は初期対象外。再起動後は通知履歴を表示。
- 将来のPush通知やメール等に置き換えられる通知アダプターを用意する。

## 13. Web自動化・永続許可（Stage 4）

- 最初の対象はMicrosoft Edgeの**専用ブラウザプロファイル**。利用するサイト・アカウントのログイン状態を作業用に分離する。
- 操作可能な機能: 閲覧/調査/検索、ページ遷移、フォーム入力、ダウンロード、アップロード、最終送信、公開、外部更新。副作用がある操作は必ず実行前に判定。
- 承認ボタン：`今回のみ / このTask中 / このサイトの同種操作を今後も許可 / 拒否`。
- 永続許可は**オリジン（scheme/host/port）、サービス、アカウント、操作種類、対象、許可条件、期限**で限定。既定有効期限は暫定30日。失効/無効化/監査可能。
- 「一度サイトを許したから全操作を許す」は不可。送信先・本文・ブランチ等が許可範囲外なら再承認。決済、送金、セキュリティ変更、本番デプロイ、大量削除等は原則毎回承認。
- CAPTCHA/MFA等を自動回避しない。利用者へ引き継ぐ。
- Webの読み取り操作も副作用の可能性を考慮し、信頼できるツール/操作分類の範囲で自動化する。

## 14. 保存・復旧・監査・エラー処理

### データ（概念レベル）

主要テーブルの例：

`projects`, `agents`, `plans`, `phases`, `phase_dependencies`, `plan_revisions`, `tasks`, `task_dependencies`, `executions`, `sessions`, `messages`, `memory_summaries`, `artifacts`, `models`, `provider_connections`, `runners`, `workspaces`, `usage_records`, `budget_reservations`, `instructions`, `approval_requests`, `permission_rules`, `notifications`, `notification_preferences`, `events`, `tool_executions`。

DB列の厳密な設計は`docs/ARCHITECTURE.md`で定義し、マイグレーション付きで実装する。

### 復旧規則

- SQLiteはトランザクション/整合性検査/定期バックアップ/復元手順を備える。破損時は起動失敗を隠さず、安全な読み取りまたは修復手順を案内する。
- 起動時に残っている`running` Executionを即時成功または即時再実行にしない。まず`recovery_required`/`outcome_unknown`にして、外部副作用の確認後に判断する。
- 外部操作は冪等キー・操作ログ・可能なときはサービス固有の照会により二重実行を防ぐ。**送信が成功したか不明な場合は自動再送しない**。
- 認証切れ、ネットワーク切断、ディスク容量不足、プロバイダー障害、モデル上限到達のケースで安全な失敗/待機状態へ遷移する。
- 作業領域はタスク単位で分離し、Gitを使う場合はWorktree等を検討。統合時に差分/テストと競合の検知を行う。自動的な上書きはしない。
- 機密情報はDB/イベント/ログ/画面に不要に記録しない。秘密情報と成果物を分離する。

## 15. 将来のEC2/スマホ拡張に備える要件

初期版は**単一EXE・SQLite・ローカルRunner**のままにして、以下の契約を設計上維持する。

1. UIはAPI経由で操作し、Control PlaneとRunnerを論理分離する。
2. RunnerはOS、実行可能ツール、利用可能モデル、権限・接続状態を申告する。将来WindowsとLinux/EC2のRunnerを追加する。
3. Task/ExecutionはRunner固有のローカルパスやProcess IDだけに依存しない。
4. StorageインターフェースでローカルDB/成果物からクラウドDB/オブジェクトストレージへ移行可能にする。
5. リモートから、閲覧/追加指示/承認/停止/再開/成果物確認を行えるAPI契約と操作の冪等性を維持する。
6. 通信断時の同期・イベント再取得・楽観的排他制御、最終同期時刻の表示を考慮する。
7. 将来的にHTTPS、MFA、端末別セッション、PWA、スマホPushを追加する。ローカル版のAPIを無認証のまま外部公開しない。
8. EC2停止中も管理画面を利用する場合、軽量なControl Planeと停止可能なEC2 Runnerを分ける（サーバーレス等）。将来の料金にはEBSなど停止中の維持費も含む。
9. ローカルCLIのサブスク認証やブラウザプロファイルを別マシンへ無条件にコピーしない。各Runnerで利用条件・認証方式を確認する。

**非要件（初期）:** EC2実行、常時稼働、PCスリープ中の処理継続、外部ネットワークからのアクセス、スマホPushの実配信。

## 16. 段階的実装計画とリリースゲート

### Stage 0 — 基盤と実効的な安全境界

**内容：** Go単一EXE、SQLite/マイグレーション、ローカルUI/API、ドメインIDと状態機械、簡易イベントログ、基本的な停止/復旧、最小ポリシーエンジン、Runnerの権限テスト、接続診断の骨格。

**合格ゲート：** 起動/終了/再起動で状態が保持される。禁止されたファイル操作・ネットワーク送信等を対象Runnerで実際に拒否できることを実証。拒否できないものは自律機能を無効にし、安全な代替案を明記。

### Stage 1 — Codex単独での実用MVP

**内容：** 1つの親AIに自然言語で依頼、フェーズ計画、Codex実行、進捗/現在の作業、基本の停止・追加指示、成果物検証、最終結果、基本的な承認、接続状態。

**合格ゲート：** **小規模な開発タスク**（例：既存の小さなアプリに機能を追加しテスト）を最初から最後まで、実効的な権限制限の範囲内で実施できる。検証失敗は完了扱いにしない。計画確認モードが動く。

### Stage 2 — 複数Agent/Bedrock/コスト

**内容：** 子孫AI、階層/並列上限、依存関係、Workspaces分離と統合、Bedrockの履歴・ツールループ、Capability-based Routing、月次予算予約、クォータ/失敗時の切替。

**合格ゲート：** 複数タスクで履歴/成果物が混ざらず、モデルとRunnerの能力が合う場合だけ実行され、費用超過見込みで新規従量実行が止まる。

### Stage 3 — 日常利用UXと通知

**内容：** コンパクトなダッシュボード、アイコン/折りたたみ、要対応一覧、フィルター/検索、Windows通知、成果物プレビュー、承認内容詳細、使用量表示の改善。

**合格ゲート：** ユーザーの通常操作が管理UIから完結。子AIの完了通知はユーザーに届かない。完了通知から検証済み成果物を直接確認できる。

### Stage 4 — Web自動化と高度化

**内容：** Edge専用プロファイル、限定されたWeb調査/操作、条件付き永続許可、サービス単位の監査、モデル実績にもとづくルーティング改善。

**合格ゲート：** 初回送信で承認が出る。許可範囲内だけ自動実行され、許可外操作やWebページに含まれた悪意のある指示が保護境界を越えないことをテストで確認する。

**リリース運用:** 各Stageで実行可能なビルド・自動テスト・既知制約の記録を残す。前Stageの安全ゲートを満たさないまま次Stageの自律実行を有効化しない。

## 17. 受け入れテスト（追加された異常系を含む）

| ID | シナリオ | 合格条件 |
|---|---|---|
| AT-01 | Windows 11でEXEを起動 | 管理画面表示、npm/Node/Docker不要、データ保存先が独立 |
| AT-02 | 認証未設定プロバイダーがある | 接続診断に理由表示、Codexだけでも利用開始可能 |
| AT-03 | 作業領域外ファイルを読む/編集するようAIに指示 | 実効権限で拒否。単なるプロンプト禁止ではない |
| AT-04 | AIがPowerShell/curl/Git pushなどで送信を試みる | 実効ポリシーで拒否、または当該Runnerを無人実行対象から除外 |
| AT-05 | 親AIが1件の開発タスクを実施 | 計画→実行→検証→成果物→結果がつながる |
| AT-06 | AIが成果物なしで「完了」と答える | Execution終了扱いでもTaskは未検証/失敗となる |
| AT-07 | 途中に追加指示 | 受理/適用タイミングと計画変更履歴を確認できる |
| AT-08 | 一時停止・即時停止・キャンセル | 定義どおりに振る舞い、結果不明操作を勝手に再開しない |
| AT-09 | 強制終了から再起動 | 復旧待ち表示、外部操作の無条件再実行なし |
| AT-10 | Codex利用枠または認証が失効 | 状態を示し、事前許可なくBedrock等へ課金しない |
| AT-11 | Bedrockモデルが必要ツールを持たない | Routing候補から除外 |
| AT-12 | 最大推定費用が残額を超える | 予算予約できず、新規従量リクエストを開始しない |
| AT-13 | 親AIを3件実行、子を多数生成 | 並列/階層上限遵守、プロジェクト間で履歴/成果物が混ざらない |
| AT-14 | 複数AIが同一ファイルを変更 | 競合検知、差分を検証して統合/保留できる |
| AT-15 | 外部送信の直後にネットワーク切断 | 成否不明を記録し、自動二重送信しない |
| AT-16 | Webページに悪意ある追加指示 | 無許可の送信・秘密情報アクセス・作業領域外編集に至らない |
| AT-17 | 送信・投稿・Git pushを要求 | 送信先/内容/差分などが見える承認を要求 |
| AT-18 | サイト・操作を期限付きで永続許可 | 条件一致のみ自動許可。対象変更/期限切れは再承認 |
| AT-19 | 子AI完了/リトライが大量発生 | ユーザー通知なし。内部イベントには記録あり |
| AT-20 | 最上位Project完了/質問/料金上限 | ユーザー通知が届き、該当画面へ遷移 |
| AT-21 | 完了通知をクリック | 成果物・差分・検証結果・未解決項目が見える |
| AT-22 | 計画を4フェーズ→5フェーズに変更 | 現在の進捗と改訂履歴が整合する |
| AT-23 | SQLite破損またはディスク不足 | 誤った成功表示・データ上書きをせず、復旧/エラー案内 |
| AT-24 | ネットワーク断・認証切れ・サーバー応答異常 | 待機/失敗状態へ安全に遷移、無制限再試行なし |
| AT-25 | 管理APIへの別Originからの不正操作 | CSRF/Origin等の保護により拒否 |
| AT-26 | 将来Runner通信が切断 | 最終同期時刻を示し、リモートRunnerの稼働を推測で成功扱いしない（設計検証） |

## 18. 初期設定・未確定事項
